# Campus Inventory API

[![Tests](https://github.com/ZidaneNaufal1/campus-inventory-api/actions/workflows/tests.yml/badge.svg)](https://github.com/ZidaneNaufal1/campus-inventory-api/actions/workflows/tests.yml)

A local development API for campus labs to explore lending equipment: register assets and borrowers, lend one unit, return it, and check availability. It uses SQLite transactions and Python's standard library. This **v0.1.0 MVP** is a foundation for a larger open-source project; it is not a production service.

**Python 3.10–3.14 · no runtime dependencies · MIT · OpenAPI 3.0.3**

## Try the local demo

```console
git clone https://github.com/ZidaneNaufal1/campus-inventory-api.git
cd campus-inventory-api
python examples/run_demo.py
python -m unittest -v
```

On Windows, use `py -3` if `python` is unavailable. The demo runs a temporary server on 127.0.0.1 with a random port and a temporary SQLite database. It creates a projector and two synthetic borrowers, verifies duplicate and unavailable loans are rejected, returns a loan, and checks availability. No external service is contacted; the temporary database is cleaned up.

```text
Demo passed: created asset and borrowers; duplicate and unavailable loans rejected; return restored stock.
Local temporary database only; no external service contacted.
```

## Run the API locally

```console
python inventory.py --db inventory.db --port 8768
```

Stop it with Ctrl+C. A new database is created if needed; existing foreign files and unsupported schemas are rejected. The server always binds to `127.0.0.1` and uses no authentication. Use synthetic data only. Do not expose it through a tunnel, reverse proxy, public deployment, or shared writable demo: authentication and authorization are planned for a later milestone.

With the server running, a second terminal can inspect the OpenAPI description at `http://127.0.0.1:8768/openapi.json`. The version-controlled [openapi.json](openapi.json) is the same document. The included demo is the easiest way to try a complete flow without manually sending requests.

## API behavior

All endpoints return JSON. POST requests require `Content-Type: application/json`, one valid Content-Length, and a body up to 65536 bytes; chunked and compressed requests are not supported. Request objects reject extra or duplicate keys. Names are trimmed and must contain 1–100 characters without control characters. IDs and quantities must be integers, not booleans.

| Method and path | Request / filter | Result |
| --- | --- | --- |
| `POST /assets` | `{"name":"Projector","quantity":1}` | 201, asset with available count |
| `GET /assets` | optional `?available=true` or `false` | asset list and available units |
| `POST /borrowers` | `{"name":"Student A"}` | 201, borrower |
| `GET /borrowers` | none | borrower list |
| `POST /loans` | `{"asset_id":1,"borrower_id":1}` | 201, active loan of one unit |
| `GET /loans` | optional `?status=active` or `returned` | loan list |
| `POST /loans/1/return` | `{}` | 200, returned loan |

IDs are generated by SQLite. Quantities are 1–100000; each loan represents one unit. A borrower may have only one active loan for the same asset. A 409 response means stock is unavailable, the same borrower already has an active loan, or the loan was already returned. Missing referenced assets/borrowers/loans produce 404. Invalid input produces 400; oversized bodies produce 413; wrong content type produces 415. Storage failures produce 503. Errors are returned as `{"error":"..."}` when the request can be parsed; malformed HTTP can be rejected by the underlying server.

Lists return at most 1000 matching records ordered by ID; pagination is not implemented. Timestamps are UTC with an explicit `+00:00` offset. The API does not yet edit/delete records, record due dates, or handle multiple units per single loan.

## Why transactions matter

Each borrow operation begins `BEGIN IMMEDIATE`, checks asset/borrower existence, duplicate active loans, and remaining stock, then inserts the loan in the same transaction. The write lock serializes competing operations on SQLite. An integration test sends simultaneous requests for the final unit and checks exactly one succeeds. A trigger-induced insert failure verifies rollback leaves the asset available and no partial loan behind. Returning a loan uses the same transaction boundary and prevents a second return.

This is evidence about the tested SQLite workflow, not a guarantee of production throughput or distributed consistency. See [technical decisions](docs/DECISIONS.md) for boundaries and validation.

## Data and security boundaries

- Borrower names and loan history are stored **unencrypted** in the local SQLite file; the demo uses synthetic names. Database files are ignored by Git. Keep real student data out of examples, issues, screenshots and commits.
- No authentication, authorization, HTTPS, rate limiting, backup or audit log exists. Other local processes may reach the server. The server is for trusted local development, not public or production use.
- Database schema version and application ID are checked before using an existing database. Stable symlink/reparse paths are rejected. This is not a sandbox for hostile files or filesystem races; use a directory and database controlled by the operator.
- Socket timeout is 3 seconds, not a hard deadline for a whole request. No performance, independent security audit, actual campus deployment or user-adoption claim is made.
